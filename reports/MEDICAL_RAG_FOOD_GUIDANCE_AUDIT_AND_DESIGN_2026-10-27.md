## 1. Executive summary

1. **[VERIFIED] There is no patient-food branch.** "Food guidance" today is one field (`food_guidance`) inside the single medication answer. It is generated by the same LLM call as the interaction analysis, it is about *medication administration and medication-food interactions*, and the prompt requests it whether or not patient context exists. Nothing in the pipeline selects a mode, checks whether patient context is usable, or retrieves condition-specific nutrition evidence.
2. **[VERIFIED] Mode A already behaves almost as required** for personalized diet advice: no diet plan is generated from drug names, because the only food field is medication-scoped and must carry reviewed source wording. What it lacks is an explicit label saying this is a medication-food warning, not a diet recommendation.
3. **[VERIFIED] Mode B is not implemented.** `known_conditions` and allergies are only appended to the retrieval query and shown to the LLM as text. They never drive a food-evidence lookup, and no output field represents patient-specific food guidance.
4. **[VERIFIED] Modes C and D are not supported.** With no drug names, the pipeline stops with `NO_VALID_DRUGS` after screening patient context.
5. **[VERIFIED] The evidence cannot support condition-specific nutrition guidance today.** The live corpus `LIVE_MEDICAL_CORPUS_V2.json` has 14 chunks, all medication labels or medication papers. None is nutrition or condition-diet evidence. The only food-specific candidate, FOOD-0001 (lisinopril / potassium-containing salt substitutes), is a *medication-food interaction*, and it is still `CANDIDATE_PENDING_RESEARCHER_APPROVAL`.
6. **[VERIFIED] In the committed data, no food statement can be released at all.** No corpus chunk carries reviewed `supported_claims`, so every `food_guidance` statement fails closed. Because release is all-or-nothing, any generated food item withholds the whole answer. Also, no V2 evidence is approved, so no chunk has a verified source identity and the live corpus abstains before generation.
7. **[PROPOSAL] The smallest correct design:** a deterministic mode decision before retrieval; keep the existing `food_guidance` as the medication branch's *medication-food interaction* output (unchanged gate); add a separate, LLM-free `patient_food_guidance` stage that runs only in Mode B, releases only researcher-approved, reviewed wording tied to a confirmed condition or instruction, flags conflicts with medication-food records, and can never change the medication verdict. Until nutrition evidence is approved, this stage would truthfully report `NO_APPROVED_EVIDENCE` in Mode B.

### Conditions under which "food" runs today [VERIFIED]

- Food guidance is **requested from the LLM on every analysis that reaches generation** (Modes A and B alike). There is no condition on patient context.
- It is **released** only if: the medication branch reached generation (eligible evidence exists), every statement of the answer is SUPPORTED, and every cited chunk carries reviewed `supported_claims`.
- It is **not run** when the pipeline abstains before generation, or when there are no drug names.

## 6. Can the available evidence support the requested food guidance? [VERIFIED]

**No, not today.**

- `LIVE_MEDICAL_CORPUS_V2.json` (14 chunks): 11 DailyMed medication label chunks, 2 PubMed chunks, 1 openFDA adverse-event chunk. Food-related text appears in three chunks, all medication-food content:
  - `DAILYMED-SPL-ATORVASTATIN-005-CHUNK-01` — with or without food; large quantities of grapefruit juice.
  - `PUBMED-PMID-31234567-CHUNK-01` — ACE inhibitors with potassium supplements / potassium-sparing diuretics / potassium-containing salt substitutes → hyperkalemia.
  - `PUBMED-PUBMED-31234567-001-CHUNK-01` — oral targeted therapies (nilotinib, pazopanib) on an empty stomach. Already shown to be unable to ground lisinopril food guidance (`test_live_evidence_provenance.py` L230).
- **No chunk carries reviewed `supported_claims`**, so the food gate (L1431) fails every food statement in the committed corpus.
- **No condition-diet or nutrition evidence exists** (no CKD diet, diabetes nutrition, sodium/potassium guidance by condition, etc.).
- The only curated food item, **FOOD-0001** (`tests/fixtures/food_0001_candidate/`), is DailyMed lisinopril §5.5: salt substitutes as a hyperkalemia *risk factor* with monitoring. Its manifest explicitly says it does **not** support "avoiding all potassium-containing foods", "any daily potassium limit or diet plan", a severity grade, or stopping a medicine, and that the passage "sets no potassium limit and no diet". Status: `CANDIDATE_PENDING_RESEARCHER_APPROVAL`, `approval: null`.
- `data/live_medical/relationships/` has no `v2/` folder, so no V2 evidence is approved; REL-LIVE-0003 (lisinopril–spironolactone, `UNGRADED`) is also pending and is rejected by the loader even if approved (`test_live_evidence_provenance.py` test J).
- Spironolactone appears in no live corpus chunk. **[INFERENCE]** The lisinopril + spironolactone example therefore cannot produce an answer on the live corpus; it would abstain before generation.

Conclusion: a patient-food branch can be built and tested end-to-end only with **test-approved fixture evidence** in a scratch relationship directory (the method the earlier rounds used). Real output would require the owner to approve a nutrition evidence source and a researcher to review each record (decision F2). I will not add or fabricate a corpus.

## 7. Proposed minimal conditional-flow design [PROPOSAL]

### 7.1 Deterministic mode decision (no LLM)

A pure function, called after screening and before retrieval:

```
decide_mode(drug_names, patient_context) -> AnalysisMode
  has_meds    = at least one drug name after sanitisation
  usable_ctx  = at least one CONFIRMED known_condition or dietary_instruction
                (age/sex alone are not enough to justify food guidance)
  A: has_meds and not usable_ctx
  B: has_meds and usable_ctx
  C: not has_meds and usable_ctx
  D: neither
```

The mode, and the reason for it, are emitted as a new `analysis_mode` SSE event and stored in the response. The LLM never decides whether to produce food guidance.

### 7.2 Two branches, one shared front end

```
input validation → (mode decision) → medication normalisation → patient-context validation
   ├─ MEDICATION BRANCH (Modes A, B) — existing pipeline, unchanged gates
   │     retrieval → security → trust → single LLM call → claim verification → answer gate
   │     outputs: interactions, adverse_reactions, warnings,
   │              food_guidance  (= medication-food interactions; same gate as today),
   │              patient_considerations
   └─ PATIENT-FOOD BRANCH (Mode B only; Mode C only if F1 approves) — new, LLM-free
         confirmed conditions / dietary instructions
         → lookup in APPROVED nutrition records only (claim_category = CONDITION_DIET)
         → keep a record only if its condition term matches a confirmed patient condition
         → release the record's reviewed wording + [Source] link (as reviewed_food_lines does)
         → conflict check against released medication-food items and stated dietary instructions
         → classify: recommended | limit | avoid | insufficient_evidence | conflict
→ final response: sections composed side by side; neither branch reads the other's evidence
```

Design properties:
- **Medication verdict isolation.** The food branch runs after the medication answer gate, reads its released output only for the conflict check, and has no write path to `claims`, `gate_decision`, `interactions` or `food_guidance`. A test asserts byte-equality of the medication section with the food branch on and off.
- **No extra LLM call and no new provider.** Patient-food items are reviewed wording from approved records, so there is nothing to generate and nothing to paraphrase. This follows the precedent in `reviewed_food_lines` and avoids the NLI over-entailment problem recorded in Round 3.
- **No new retrieval engine.** Approved nutrition records load through the existing V2 loader (`load_relationship_store`, `standalone_evidence_chunks`) with a new `claim_category`, and are selected by exact record fields, not by vector search. They are **excluded from the medication branch's evidence block**, so they cannot ground a medication claim, and medication chunks cannot ground a food item.
- **No change** to the NLI model, prompt text or hash, trust formula, thresholds, eligibility, citation rules or the medication answer's all-or-nothing abstention.
- **Missing evidence is an outcome, not an error.** Mode B with no matching approved record releases a `patient_food_status` of `NO_APPROVED_EVIDENCE` and a one-line explanation, never filler.
- **When the medication branch abstains** (recommended default, decision F4): the patient-food section is withheld with reason "medication analysis was withheld, so conflicts with your medications could not be checked".

### 7.3 Medication-food warnings stay in the medication report

The existing `food_guidance` field is kept as is in the backend (same gate, same reviewed-wording release). Only its presentation changes: the UI section is titled "Medication–food interactions" in every mode, and its empty-state text stops mentioning diet. It is never shown as a personalised recommendation.

### 7.4 Mode C and D responses

- Mode C (recommended for now, decision F1): no analysis; a specific message, "Food guidance from patient details alone is not supported in this version. Add the medications to analyse, or ask a clinician about diet for this condition." No drug analysis is fabricated.
- Mode D: a validation message naming what is needed (at least one medication; optionally confirmed conditions or dietary instructions).

## 8. Proposed schema and API changes [PROPOSAL]

All additive and backward-compatible. Existing clients keep working.

### 8.1 `PatientContextInput`

```
dietary_instructions: list[ContextItem] = []     # existing diet / clinician nutrition instructions
food_allergies_intolerances: list[ContextItem] = []
known_conditions: list[str | ContextItem]        # str is accepted and read as USER_ENTERED + CONFIRMED

ContextItem:
  text: str                                       # screened like today
  source: USER_ENTERED | DOCUMENT_EXTRACTED       # MODEL_INFERRED is not accepted at all
  confirmation: CONFIRMED | UNCONFIRMED
```

- Only `CONFIRMED` items count toward `usable_ctx` and food matching. `UNCONFIRMED` items are shown under "Patient context used" with "unconfirmed: not used".
- `known_allergies` stays (drug allergies). Whether to split food allergies out of it is decision F3.
- `diabetes` / `hypertension` booleans from the spec are **not** recommended; they duplicate `known_conditions`.

### 8.2 Response

```
analysis_mode: "A" | "B" | "C" | "D"
analysis_mode_reason: str
patient_food_guidance: list[PatientFoodItem] = []
patient_food_status: VERIFIED | NO_APPROVED_EVIDENCE | NO_RELEVANT_CONTEXT | WITHHELD_MEDICATION_ABSTAINED | NOT_APPLICABLE
patient_context_used: per-item text, source, confirmation, used: bool, reason_not_used
food_guidance_status: added to AnalyzeResponse (already emitted; currently untyped)
input_mode: real value instead of the hard-coded "direct_drugs"

PatientFoodItem:
  food_or_action: str
  classification: recommended | limit | avoid | insufficient_evidence | conflict
  basis: { kind: CONDITION | DIETARY_INSTRUCTION | MEDICATION, value: str }
  reviewed_text: str            # the approved reviewed wording, verbatim
  source: { chunk_id, url, source_identity_status, passage }
  qualifiers: list[str]         # from the record; never generated
  scope: PATIENT_SPECIFIC | GENERAL_INFORMATION
  conflicts_with: list[str]     # ids of medication-food items or instructions
  record_id, approval
```

### 8.3 Approved nutrition record (data contract; no data proposed)

V2 standalone evidence with `claim_category: CONDITION_DIET`, `condition` (term plus code if available), `population`, `food_entity`, `direction`, `supported_claims` (reviewed wording and action level), `not_supported`, source identity, `status`, and named-researcher `approval`. This mirrors the FOOD-0001 manifest.

### 8.4 Frontend

Separate sections A–D as in the brief: "Medication analysis", "Medication–food interactions", "Patient-specific food guidance" (only in Mode B, and only populated or with one honest status line), "Patient context used", "Limitations". Render `patient_considerations`, which is currently dropped. Add the dietary-instruction input and confirmation state. Correct the `food_relationship` type union.

## 9. Regression tests and measurable acceptance criteria [PROPOSAL]
