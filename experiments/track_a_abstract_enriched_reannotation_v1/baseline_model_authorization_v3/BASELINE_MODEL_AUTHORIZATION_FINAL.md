## Explicit Answers to Required Questions

### 1. What exact semantic embedding model is authorized by the research protocol?

**No protocol document explicitly authorizes a specific embedding model.**

The `FREE_REPLICATION_V1_PROTOCOL.md` is silent on the embedding model. The `FREE_REPLICATION_V1_CONFIG.json` contains only LLM provider/model settings. The `CURRENT_ARCHITECTURE_SNAPSHOT.md` is a descriptive snapshot of code state, not a normative protocol.

However, the project's architecture document (`docs/ARCHITECTURE.md`) specifies `VECTOR(768)` for the evidence_chunks table, which is **incompatible** with `SimpleEmbeddingModel` (7-dim) and **compatible** with `pritamdeka/S-PubMedBert-MS-MARCO` (768-dim).

### 2. Where is that authorization documented?

There is no single authoritative document. The closest evidence is:
- `experiments/runs/fusion-evaluation-v3-real/manifest.json` — records `"embedding_model": "pritamdeka/S-PubMedBert-MS-MARCO"`
- `experiments/runs/fusion-evaluation-v3-confirmed/manifest.json` — records the same model
- `docs/ARCHITECTURE.md` — specifies `VECTOR(768)` implicitly requiring a real transformer model
- 11+ experiment scripts in `scripts/` — all use `RealEmbeddingModel(SentenceTransformer("pritamdeka/S-PubMedBert-MS-MARCO"))`

### 3. Is SimpleEmbeddingModel a protocol baseline or only a test fixture?

**It is a test fixture.**

Evidence:
- Introduced in commit `ea97355` (2026-08-23) alongside `SimpleLLMBackend` to replace a mock ablation engine
- Never described as "baseline", "production", or "authorized" in any commit message
- Its 7-word vocabulary and 7-dim output are incompatible with the `VECTOR(768)` schema in `docs/ARCHITECTURE.md`
- The same commit that created the architecture snapshot (`b18461d`) captured it merely as "the current code state"
- The experiment scripts that perform actual retrieval evaluation use `RealEmbeddingModel` with `S-PubMedBert`, not `SimpleEmbeddingModel`

### 4. What exact runtime code generated the current baseline retrieval evidence?

The V2 runtime evidence was generated by:
- `experiments/runtime_retrieval_proof_v2.py` — instantiates live `HybridRetrievalEngine` and `cognee.search()` 
- `experiments/fast_phase9.py` — instantiates live `AdaptiveTrustRAGOrchestrator`

These scripts serialize direct return values from live function calls. The V1 evidence (`generate_repair_artifacts.py`) was programmatically hardcoded and is invalid.

### 5. Is the current runtime evidence genuinely captured or partially generated?

The V2 evidence is **genuinely captured** from live runtime objects, except for one placeholder field (`source_file_hash: "f3d5..."`). The V1 evidence was **entirely generated** and must be discarded.

### 6. Can POS-01, POS-02 and RG-02 retrieve genuine candidates through the current implementation?

**Partially.** BM25 retrieves candidates for queries containing words in the corpus. The dense channel is non-functional for POS-01 and RG-02 because `SimpleEmbeddingModel` produces zero vectors for those queries. The Graph channel returns candidates only when drug relationships are pre-loaded (which is not default).

### 7. Would changing the embedding model invalidate comparability with prior experiments?

| Prior Experiment | Model Used | Comparability if changed to S-PubMedBert |
|---|---|---|
| fusion-evaluation-v3-real | S-PubMedBert-MS-MARCO | **COMPARABLE** |
| fusion-evaluation-v3-confirmed | S-PubMedBert-MS-MARCO | **COMPARABLE** |
| retrieval-baseline-v1 | SimpleEmbeddingModel | NOT_COMPARABLE |
| retrieval-baseline-v2_1 | SimpleEmbeddingModel | NOT_COMPARABLE |
| f0-f1-v2 | SimpleEmbeddingModel (DETERMINISTIC-MOCK) | NOT_COMPARABLE |
| FREE_REPLICATION_V1 | SimpleEmbeddingModel | NOT_COMPARABLE |

Switching to `S-PubMedBert` would restore comparability with the fusion-evaluation experiments (which are the most rigorous retrieval evaluations) but break comparability with experiments that used `SimpleEmbeddingModel`.

### 8. What exact decision is required before Full Gate 5 can proceed?

The research lead must explicitly decide:

> **"Is `pritamdeka/S-PubMedBert-MS-MARCO` the authorized dense embedding model for the Gate 5 baseline?"**

If yes:
1. Freeze the exact HuggingFace revision hash
2. Replace `SimpleEmbeddingModel` with `RealEmbeddingModel` in the orchestrator baseline path
3. Re-run retrieval qualification with the new model
4. Document that this makes results incomparable with prior `SimpleEmbeddingModel` experiments

If no:
1. Identify what model is intended
2. Or explicitly authorize `SimpleEmbeddingModel` as a deliberate constraint and document the limitation
